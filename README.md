# Jpay

一套面向互联网企业的开源支付系统，以**对账引擎为核心**，主打生产可用的轻量级收单与对账能力。

---

# 项目背景

## 一句话定位

> Jpay 是一个以**对账引擎为核心**、可独立部署的生产级轻量级收单与对账系统，面向中小支付机构和 Java 后端，把多渠道收单、T+1 多方对账、差错处理与 AI 归因做成开箱即用的能力。

## 痛点背景

支付系统的复杂度集中在两端：上游对接一堆渠道，下游面对海量交易与商户。但真正最容易被低估、也最折磨团队的是**对账**——它不性感，却是资金安全不可逾越的底线。

- **对账长期被当作"附属功能"**。市面上的开源支付方案大多在收单、商户进件等前端能力上卷功能，对账往往只是配套模块，规则浅、扩展性差，遇到真实的多方勾稽场景就力不从心。
- **多方对账自研成本高、风险大**。渠道账、商户账、内部账三方数据量庞大、规则各异，差错类型繁多（长款、短款、挂账、状态不一致）。从零自研一套可靠的核对引擎，周期以月计，且极易在大促或边界场景下出错。
- **T+1 跑批与差错处理高度依赖人工**。很多团队仍在用定时脚本 + 人工拉表 + 肉眼比对的组合，效率低、不可审计、难以复盘，夜间跑批出问题常常靠值班人员"救火"。
- **出错后缺乏系统化归因**。一笔差错背后的根因可能是渠道回调延迟、幂等缺失、状态机跳转异常或脏数据，缺乏结构化归因手段时，定位根因全凭经验，问题反复出现。

## "生产可用"的定义

Jpay 标榜"生产可用"不是营销话术，而是用一套工程基线来保证的：

- **数据一致性有兜底**：核心资金链路引入 Seata 分布式事务，避免跨服务记账出现中间态。
- **流程异步解耦**：收单回调、对账触发、差错通知等通过 RabbitMQ 削峰与解耦，关键链路具备重试与幂等。
- **批处理可靠可调度**：T+1 多方对账跑批由 xxl-job 统一编排，支持失败重试、告警与执行日志可追溯。
- **规则可配置而非写死**：对账引擎将勾稽规则、抽样策略、差错判定抽象为可配置项，适配不同渠道与业务。
- **可观测、可回滚**：关键节点有状态与日志留痕，差错处理流程可追溯、可审计，符合生产环境的合规与运维要求。

> 简言之，"生产可用" = 一致性有保障、跑批不丢不重、差错能查能处理、半夜出事能定位。

## 范围边界

为避免误解，明确 Jpay 做什么、不做什么：

- **纵深优先，不做大而全**。Jpay 以对账为垂直主线，收单与商户进件是为对账提供数据与场景的配套能力，而非要做一个覆盖所有支付环节的 SaaS。
- **不内置资金清算/结算**。系统聚焦"账的对"与"错的处"，不涉及资金实际划拨、清算路由、钱包账户体系或信贷等周边域。
- **渠道以可插拔适配为主**。提供多渠道收单能力与适配框架，但不追求预置对接市面上所有第三方渠道，重点在扩展性与规范，而非渠道数量。
- **AI 归因需自行接入模型**。Spring AI 归因是架构能力，需由使用方配置模型服务与密钥，Jpay 不内置或托管任何大模型。

**与 Jeepay 的差异**：Jeepay 是横向全覆盖的开源支付 SaaS；Jpay 选择**纵向做深对账**，强调**可独立部署**、**对账引擎垂直纵深**，并原生集成 **AI 归因**——定位是"把对账这件事做到生产级"，而非"再做一个支付全家桶"。

## 适用人群

- **中小支付机构**：需要生产级对账能力，但团队规模与预算不足以从零自研一套可靠引擎。
- **Java 后端工程师**：希望落地一套真实可用的生产级支付对账实现，作为参考架构或二次开发基座。
- **技术负责人 / 架构师**：正在评估对账方案选型，需要可审阅、可改造的开源实现来做技术决策。
- **支付领域学习者**：想通过工程化代码理解多方对账、差错处理与分布式一致性的真实落地方式。
